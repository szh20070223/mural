# AI 壁画观察卡 · 数据契约

> 版本 **1.1**（2026-11-25；旧版卡片仍可读取）
> 契约本体：`src/schemas.py` 里的 `Card`
> 可运行示例：`docs/card.example.json`
> 校验命令：`python tools/check_contract.py`

---

## 1. 这份契约解决什么问题

一条流水线跑完，会有三拨人同时要用它的输出：

| 谁 | 读什么 | 产出 |
|---|---|---|
| R3 版式与视频 | `card.json` → `card.pdf` | 一页观察卡的版式 |
| R4 报告与合规 | `card.json` 的字段 | 报告正文、合规段落 |
| R3 版式与视频 | `card.pdf` + `trace` 日志 | 2 分钟演示视频的分镜 |
| R2 数据标注 | `data/labels.jsonl` | 标注集、回归测试的对照答案 |

如果大家各自猜字段名，改一次提示词就要返工三次。所以先把这个文件钉死：
**下游只认 `Card`，不认中间产物。**

---

## 2. 赛题对这张卡的硬要求

下面是规则原文里能直接对上的条目，字段设计就是照着它来的：

- 一页 PDF，**超过 1 页只评第 1 页**（所以有个"排版预算"，见第 4 节）
- 在原图上标出 **1–3 处**值得关注的区域
- 提出 **1–2 条**保护、数字展示或公众传播建议，**说明依据和可能风险**
- 明确**不确定性与人工复核提示**
- 注明**图片、公开资料和 AI 工具来源**
- 明确**哪些内容由 AI 生成、哪些需要人工复核**

当前主线 A 最多提出 5 个候选，B 逐条审查，确定性规则保留最多 3 个区域。
没有合格区域时不强行成卡，也不据此宣称壁画完好。

## 3. 字段速查表

### 3.1 卡片主体

| 字段 | 类型 | 上限 | 卡上位置 | 谁来填 |
|---|---|---|---|---|
| `schema_version` | str | — | 不显示 | 代码 |
| `image_id` | str | — | 缩略图下方图注 | 代码（取文件名） |
| `summary` | str | **80 字** | 标题下一行 | C 成稿 |
| `regions` | list | **1–3 个** | 缩略图上的编号框 + 三栏说明 | B 裁决后 |
| `recommendations` | list | **1–2 条** | 右侧/下方建议区 | C 成稿 |
| `limitations` | list | **3 条** | "看不清的地方"小字区 | C 成稿 |
| `review_status` | 枚举 | — | 右上角徽章 | 人工复核后改 |
| `disclaimer` | str | — | 页脚 | 代码（固定文案） |

### 3.2 单个区域 `regions[]`

| 字段 | 类型 | 上限 | 说明 |
|---|---|---|---|
| `region_id` | `R1`–`R9` | — | 和缩略图上的框编号一致 |
| `disease` | 8 类枚举或待判读 | — | “待判读”表示可见异常存在，性质未确认；不是第九种病害 |
| `source_candidate_ids` | list[str] | — | 追溯到 A/B 的 C 编号；旧卡可为空 |
| `bbox` | `[x1,y1,x2,y2]` | 0–1 | 归一化坐标，原点左上 |
| `observation` | str | **60 字** | 只写看到的：颜色、边界、纹理、走向 |
| `impact` | str | **40 字** | 对画面内容的影响：挡住了什么、让哪部分无法辨认 |
| `confidence` | 高/中/低 | — | 三档，没有"无法评估" |
| `review_notes` | list | **2 条 × 30 字** | 具体到"做什么"的复核点 |
| `ai_generated` | bool | — | 默认 true |

`confidence` 是模型自评的高/中/低，未经统计校准，不能解释成概率或严重程度。
可定位但类别不明的异常可以列“待判读”、低置信度，并明确要补充的证据；
一般性的图像不足写入 `limitations`。

### 3.3 建议 `recommendations[]`

| 字段 | 上限 | 说明 |
|---|---|---|
| `action` | 60 字 | 建议做什么 |
| `basis` | 60 字 | 依据：对应哪个区域、为什么这么建议 |
| `risk` | 40 字，**不能为空** | 这条建议可能带来什么问题 |
| `needs_human_review` | — | 默认 true |

`risk` 不能空，也不能用“无风险”等空泛表述代替实际风险。
`basis` 必须引用本卡真实存在的区域，R10 不会被当作 R1。

### 3.4 来源 `provenance`

| 字段 | 说明 |
|---|---|
| `image_source` | 图片从哪来。命题方提供 / 数字敦煌 / 自摄 / URL，必须能追溯 |
| `image_license` | 授权情况。**没写清楚 = 这张卡不合规** |
| `scene_note` | 用户提供的场景资料；传给三阶段作背景，不能替代图像证据 |
| `platform` | 默认「阿里云百炼（DashScope）」。现场赛只认百炼 |
| `models` | 实际模型全名，如 `["qwen3.8-max"]`。写错很扎眼 |
| `prompt_version` | 提示词版本（git 短哈希或手写号）。没版本号就没法回滚和追责 |
| `tools` | 除模型外的工具，开源库也要写 |
| `generated_at` | ISO8601 |
| `run_id` | 与 `trace` 日志一一对应 |
| `input_sha256` | 本次输入快照的 SHA-256，旧卡默认空 |
| `prompt_hashes` | 三段提示词模板摘要，模板快照保存在 `output/inputs/{run_id}/prompts/` |
| `evidence_path` | 审查后区域与候选映射文件相对路径，旧卡默认空 |

赛题原文：「隐瞒第三方 AI 工具使用情况」会取消成绩。所以这几个字段是保命字段。

### 3.5 归属 `attribution`

| 字段 | 说明 |
|---|---|
| `ai_generated` | 哪些内容是模型写的 |
| `human_review_required` | 哪些必须人看过才能用 |
| `human_reviewed` | 已经人工确认的部分。**空列表 = 还没复核** |
| `reviewer` | 复核人姓名 |

代码里有硬校验：`review_status` 一旦不是"待人工复核"，`reviewer` 和
`human_reviewed` 都不许为空。**空口标"已复核"在数据层就存不下来。**

## 4. 排版预算：为什么字数上限是这些数

一页 A4（2480×3508 @300dpi）的版面按比例切：

| 区块 | 占比 | 备注 |
|---|---|---|
| 页眉（标题 + 图号 + 复核徽章） | 8% | |
| 缩略图（含标记框） | 38% | 约 210×110 mm，是整页的视觉主体 |
| 三个区域说明 | 22% | 每块约 5 行 |
| 建议区 | 12% | |
| 局限性 + 归属 + 来源 | 18% | 小字，但要能看清 |
| 页脚（免责声明） | 2% | |

早期预算以约 **1100 字**估算（下面不是当前渲染器的字号保证）。按字段长度估算：
`3 区域 × (60+40+60) + 2 建议 × 160 + 总述 80 + 局限 90 + 来源 150 ≈ 1050 字`。

以上是早期估算。当前渲染器先测量所有文字，再在设定范围内调整正文字号和缩略图高度。
完整内容仍放不下一页时明确报错，保留 JSON，不导出被截断的卡片。

> 做版式时请直接用 `docs/card.example.json`，它已经填满了字数上限。
> 来源和复核说明可变长，因此还应检查实际卡片，示例不能证明任意文本均可排下。

## 5. 关于示例文件

`docs/card.example.json` 有三点要说清楚：

1. **框是示意坐标**，不是模型真实输出。真实坐标由 A 生成、B 调整。
2. 里面用的是 `test_mural1.png` 这张本地测试图，**不是命题方材料**，
   所以 `image_license` 写的是"仅用于本地调试"。正式提交时这一栏必须换成真实授权说明。
3. 示例与真实程序默认均为“待人工复核”，没有真实复核人和记录时不能标为已复核。
   需要覆盖已复核版式时，请只在明确标识的测试样例中填入模拟字段。

## 8. 中间数据与复核约束

- A `findings` 和 B `verdicts` 必须明确提供数组，缺失/null 是异常，不能等同于未检出。
- B 必须完整且仅覆盖 A 的候选；编号不重复，漏项/未知项进入一次格式纠正重试。
- 决策为 keep、adjust、drop、merge、defer。adjust 可改框、类别、置信度或文字；改类别或 defer 必须同时修订 observation 与 impact。
- defer 输出“待判读”、低置信度。merge 直接指向保留项；不接受链、循环、不同类别或不相交区域。
- IoU 仅对同类重复项去重，不提高合并后的置信度；按 B 输出顺序保留最多三个区域。
- A、B 以及 C 的局限合并保留，超三项时分组，不让 C 删除上游约束。完整中间数据独立保存。

## 6. 五条禁止

1. **不要改字段名。** 要改就改 `schemas.py` + 本文档 + 示例，三处一起，然后跑校验。
2. **`risk` 不许留空。**
3. **`regions` 不许超过 3 个。** 超了就不是这个赛题的交付物。
4. **不许编来源。** 来源不明的图不要进卡，宁可换图。
5. **不许在渲染器里塞私有字段。** `Card` 开了 `extra="forbid"`，
   多写一个未声明的键会直接报错——这是故意的，防止只有一个人机器能跑的"临时代码"。

## 7. 改契约的流程

```
① 改 src/schemas.py（改完先想清楚谁会受影响）
② 改 docs/card-contract.md（本文档）
③ 改 docs/card.example.json（让示例保持可运行）
④ python tools/check_contract.py   ← 必须全绿
⑤ 在群里说一句：契约升到 x.y，字段有/没有变化
```

示例跑不过 = 契约写错了，**不是示例写错了**。改示例去迁就代码，等于把接口偷偷改了。
